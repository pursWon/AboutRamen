문제 : 라멘 이미지들을 데이터 통신을 하여 가져오는 것이 어려웠음

- 가게 이미지를 가져오는 API의 파라미터로 가게이름(`storeName`)이 필요했음.
    - 기존에 가게 리스트를 가져올 때 저장한 `storeNames` 배열을 활용하기로 결정.
    - storeNames 에 대해 for문을 돌려 `getRamenImages`(이미지 데이터를 가져오는 데이터 통신을 하는 함수)의 인자로 사용함.
    - `getRamenImages`의 실행 결과인 이미지 URL들을 `imageUrlList` 배열 에 담아줌.
    - `imageUrlList`를 UIImage 타입으로 바꾸어 imageView에 대입.
    
- 실행 결과`storeNames`이 빈배열이여서 이미지를 가져올 수가 없는 상황이 발생
    - 원인: 이미지를 가져오는 함수를 실행시키는 시점이 문제로 확인.
    가게 정보를 가져오는 API 호출(`getRamenData`)보다 
    이미지 정보를 가져오는 API(`getRamenImages`)가 먼저 호출되고 있었음.
    (`viewDidLoad()`에서 `getRamenImages`를 호출했기 때문)
    - `storeNames`의 배열에 필요로 하는 데이터 갯수만큼 통신이 끝난 후에 `getRamenImages` 함수 실행이 이루어져야 해당 오류를 고칠 수 있다는 것을 알게 되었음.
    - `getRamenData` 함수 안 `storeNames`의 배열에

## 업데이트 사항(ver 1.2) : 코드 전수 분석 및 기능 고도화

### 배경 및 목적

한동안 관리하지 않았던 앱을 다시 열어보면서, 실제 동작 방식과 코드 구조를 처음부터 다시 전수 분석했습니다. 그 과정에서 드러난 잠재적 버그와 기술 부채를 먼저 정리해서 고치고, 이어서 "겉보기엔 되는 것 같지만 실제로는 아쉬운" 핵심 기능들을 실사용 가능한 수준으로 보강했습니다.

### 작업 흐름

1. **전체 코드 분석** : 모든 소스 파일을 읽으며 아키텍처(MVC), 데이터 흐름(Kakao API 조회 → `RamenData` 변환 → Realm 저장 → 화면 표시), 화면·모델별 역할을 파악했습니다.
2. **API 키 유효성 점검** : 프로젝트에 하드코딩된 채 git 이력에 그대로 남아있던 Kakao API 키를 발견하고, 실제로 살아있는 키인지 REST 호출로 직접 검증했습니다.
3. **분석 중 발견한 문제 수정**
   - `RegionData.load()`가 빈 문자열 파일명(`fileName = ""`)에 의존해 우연히 동작하고 있던 것을 `"RegionInformation"`으로 명시.
   - `SearchViewCell`에 스토리보드로만 연결돼 있고 코드에서는 쓰이지 않던 `searchResultLabel` 아웃렛을 실제로 사용하도록 수정.
   - Xcode 프로젝트에 등록조차 안 되어 빌드에 포함되지 않던 고아 파일 `ReviewTextAlert.swift` 삭제.
   - Realm `schemaVersion`이 명시돼 있지 않던 것을 `AppDelegate`에서 버전(1)으로 고정해, 이후 스키마 변경 시 안전하게 마이그레이션할 수 있는 기준점 마련.
   - Kakao API 키가 담긴 `RamenInfo.plist`를 git 추적에서 제외하고 `.gitignore`에 등록, `RamenInfo.plist.sample` 템플릿을 대신 추가. 키는 재발급받아 로컬에서만 교체.
4. **핵심 기능 고도화** : 분석 과정에서 스스로 진단한 "당장 손볼 만한 기능적 아쉬움" 4가지를 개선했습니다.

### 이번에 추가/개선한 기능

- **검색 재질의**: 기존엔 최초 로드된 15건 안에서만 가게 이름을 텍스트로 걸러내던 "가짜 검색"이었던 것을, 검색어 입력 시 Kakao API에 직접 재질의(0.4초 디바운스 적용)하고 스크롤을 내리면 다음 페이지까지 이어 받는 무한 스크롤 페이지네이션으로 개선했습니다.

## 업데이트 사항(ver 1.3) : 눈에 안 보이던 버그 정리와 화면 톤 통일

### 왜 다시 열어봤나

Codemagic으로 빌드 파이프라인을 붙이고 나서 시뮬레이터 스크린샷을 받아볼 수 있게 되니, 그동안 코드로만 보던 화면을 실제 이미지로 확인하게 됐습니다. 그런데 화면을 보다 보니 톤이 제각각인 게 눈에 걸렸습니다. 검색 탭만 흰 배경이고 나머지는 베이지, 카드마다 검정 테두리가 두껍게 둘러져 있고, 같은 별점인데 화면마다 이모지였다가 하트였다가 했습니다.

디자인을 손보려고 파일을 열었는데, 색을 바꾸려면 어차피 색 지정이 흩어진 곳을 전부 찾아야 했습니다. 그 김에 소스를 처음부터 다시 읽었고, 그러다 디자인 문제보다 심각한 것들을 먼저 발견했습니다. 그래서 이번 작업은 기능 결함 수정과 디자인 정리가 같이 들어가 있습니다.

### 1. 읽다가 발견한 기능 결함

**홈 화면에서 가게와 사진이 서로 뒤바뀌고 있었습니다.**

`getRamenImages()`는 가게 이름마다 이미지 검색 요청을 띄웁니다. 그런데 요청을 동시에 보내놓고 응답이 오는 대로 `imageUrlList.append()`로 배열에 쌓고 있었습니다. 네트워크 응답이 요청 순서대로 돌아온다는 보장이 없으므로 배열 순서는 가게 순서와 달라집니다. 그런데 셀을 그릴 때는 `imageUrlList[originalIndex]`로 위치를 믿고 꺼내 쓰고 있었습니다.

여기에 더해, 사진이 없는 가게는 `if !dataImage.documents.isEmpty` 조건에 걸려 배열에 아예 들어가지 않았습니다. 그러면 그 뒤 인덱스가 전부 한 칸씩 밀립니다. `imageUrlList.count == ramenList.count` 가드가 있어서 개수가 안 맞으면 전부 기본 이미지로 빠지긴 하는데, 개수가 우연히 맞아떨어지면 엉뚱한 가게 사진이 그대로 화면에 나갑니다.

응답 순서에 따라 증상이 나타났다 안 나타났다 하는 종류라 그동안 눈치채기 어려웠던 것으로 보입니다. 배열 길이를 미리 확보한 `[String?]`에 인덱스를 지정해 넣고, `DispatchGroup`으로 모든 요청이 끝난 뒤 한 번만 갱신하도록 바꿨습니다. 사진이 없는 가게는 `nil`로 남으니 인덱스가 밀릴 일도 없습니다.

**별점만 매기면 저장이 안 되고 있었습니다.**

`deleteNoDataItem()`은 사용자가 아무 흔적도 남기지 않은 데이터를 정리하는 함수인데, 삭제 조건이 `!isGood && !isReviewed && !isFavorite`였습니다. `rating`이 빠져 있습니다.

상세 화면에서 별점을 매기면 화면을 벗어날 때 `saveData()`가 Realm에 저장합니다. 그런데 좋아요나 리뷰, 찜을 하나도 누르지 않았다면, 홈으로 돌아오는 순간 `viewWillAppear`가 `deleteNoDataItem()`을 호출해서 방금 저장한 별점을 지워버립니다. 사용자 입장에서는 별점을 매겼는데 반영이 안 되는 것으로 보입니다.

조건이 세 화면에 똑같이 복사돼 있었기 때문에, `RamenData.hasNoUserData`라는 계산 프로퍼티로 한곳에 모으고 `rating == 0`을 조건에 추가했습니다. 앞으로 판단 기준이 늘어도 한 곳만 고치면 됩니다.

**폰트 이름에 오타가 있었습니다.**

등록된 폰트 파일은 `Recipekorea.ttf`이고 코드 스무 곳 남짓이 `"Recipekorea"`를 쓰는데, 홈 화면의 "나의 지역" 라벨 한 줄만 `"RecipeKorea"`로 대문자 K였습니다. iOS는 폰트 이름의 대소문자를 구분하므로 `UIFont(name:size:)`가 `nil`을 반환하고, 그 라벨만 조용히 시스템 폰트로 떨어집니다. 크래시도 경고도 없어서 눈으로 비교해야만 찾을 수 있는 종류였습니다.

이런 오타가 다시 생기지 않도록 폰트 지정을 `AppFont`로 모았습니다. 문자열을 서른 곳에 흩뿌리는 대신 역할별 이름으로 부르니, 오타는 컴파일 단계에서 걸리고 크기를 조정할 때도 한 파일만 보면 됩니다.

### 2. 문제가 생겼을 때 사용자가 알 수 있게

모든 API 호출이 `if let data = response.value` 한 줄로 끝나고 있었습니다. 실패 케이스가 없습니다. 비행기 모드거나 API 키가 만료됐거나 카카오가 요청 제한을 걸어도 화면은 그냥 빈 채로 멈춰 있고, 사용자는 앱이 고장 난 건지 근처에 라멘집이 없는 건지 구분할 수 없습니다.

`switch response.result`로 실패를 받도록 바꾸고, 연결 자체가 안 되는 경우와 서버가 응답은 줬지만 오류인 경우를 구분해서 다른 문구를 보여주도록 했습니다. 홈 화면에는 로딩 인디케이터도 붙였습니다. 위치 확정, 키워드 검색, 가게별 이미지 검색까지 순차 호출을 거치는 동안 실기기에서는 몇 초가 걸릴 수 있는데 그 시간 동안 아무 피드백이 없었습니다.

Realm 쓰기도 전부 `try!`였습니다. 디스크가 가득 찼거나 마이그레이션이 어긋나면 그 자리에서 앱이 죽습니다. `do/catch`로 받아서 저장 실패를 알럿으로 알리도록 바꿨습니다.

검색 탭에서는 `setInitData()`가 위치 권한을 확인하는 `if` 블록 안에 들어가 있었습니다. 이 함수는 배경색과 폰트를 지정하는 일도 같이 하고 있어서, 권한을 거부하면 화면 스타일이 통째로 빠진 채로 남았습니다. 외형 설정과 데이터 로딩을 분리했습니다.

### 3. 홈과 검색 탭이 다른 지역을 보던 문제

홈에서 "지역 변경"으로 부산을 골라도 검색 탭은 여전히 원래 GPS 좌표 기준 목록을 보여주고 있었습니다. 검색 탭의 기본 목록이 최초 GPS 응답 한 번에만 로드되고, 이후 지역 변경을 알 방법이 없었기 때문입니다. 두 탭이 서로 다른 지역을 말하는 셈이라 어느 쪽이 맞는지 알 수 없었습니다.

원인을 따라가 보니 지역 정보가 `HomeViewController.swift` 파일 최상단의 전역 변수 `let region = load()`에 담겨 있었습니다. 앱 전체 네임스페이스에 노출된 데다 소유 관계도 불분명했습니다. 이걸 `RegionStore.shared`로 옮기고, 지역이 바뀌면 알림을 보내 두 탭이 함께 갱신되도록 했습니다.

### 4. 화면 톤 통일

처음에 눈에 걸렸던 디자인 문제를 정리했습니다. 방향은 진한 선을 걷어내고 색을 한 벌로 모으는 쪽으로 잡았습니다.

색은 여섯 개 토큰(`ground`, `surface`, `ink`, `inkSoft`, `accent`, `hairline`)으로 정리했습니다. 각 토큰은 라이트와 다크 두 값을 가진 다이나믹 컬러라서, 그동안 전혀 없던 다크 모드 대응도 여기서 같이 해결됐습니다. 액센트로 쓰는 주황색은 별점과 주요 액션에만 쓰기로 했습니다. 곳곳에 뿌리면 강조하는 의미가 사라지기 때문입니다.

테두리는 상세 화면이 가장 심했습니다. 주소, 전화번호, 링크, 버튼 영역에 일괄로 2pt 검정 테두리를 두르고, 사진 사이에도 검은 세로 분할선을 넣고 있었습니다. 이걸 흰 카드에 1픽셀 헤어라인과 옅은 그림자를 얹는 방식으로 바꿨습니다. 사진 사이 분할선은 지우고 모서리를 둥글려 간격으로 구분했습니다. 리뷰 화면 텍스트뷰의 2.5pt 테두리도 같은 방식으로 정리했습니다.

별점 표기는 홈이 이모지, 마이 리스트가 하트 아이콘, 상세가 커스텀 이미지로 제각각이었습니다. 전부 `star.fill`에 액센트 색으로 통일했습니다. 별점이 없을 때 "별점 없음"이라는 글자를 배지에 넣던 것도 바꿨습니다. 문구 길이 때문에 배지 폭이 들쭉날쭉해졌기 때문에, 값이 없으면 배지 자체를 숨기도록 했습니다.

상세 화면의 "좋아요", "리뷰하기", "추가하기" 라벨은 9pt였습니다. Apple 휴먼 인터페이스 가이드라인의 최소 권장이 11pt인데 그보다 작았고, 실기기에서 보면 확실히 읽기 힘든 크기입니다. 12pt로 올렸습니다.

### 5. 정리한 기술 부채

- iOS 14에서 대체된 위치 API 두 가지(`CLLocationManager.authorizationStatus()` 타입 메서드, `didChangeAuthorization` 콜백)를 현재 방식으로 교체했습니다. 타입 메서드 쪽은 메인 스레드를 막을 수 있다는 문제도 있었습니다.
- `AppDelegate`의 `sleep(1)`을 제거했습니다. 런치 스크린을 조금 더 보여주려는 의도로 보이는데, 메인 스레드를 통째로 세우는 방식이라 실제로는 실행이 1초 느린 앱이 됩니다.
- `sortedIndices()`가 셀을 그릴 때마다 호출되고 있어서, 셀 하나당 전체 목록 정렬이 한 번씩 돌고 있었습니다. 결과를 캐시하고 정렬 기준이나 위치, 별점이 바뀔 때만 다시 계산하도록 했습니다.
- `goodStoreName` 배열은 `removeAll()` 없이 `append`만 하고 있어서 위치가 갱신될 때마다 중복이 쌓이고 있었는데, 정작 읽는 곳이 어디에도 없었습니다. 선언까지 함께 지웠습니다.
- `ReviewViewController`의 `delegate`가 strong 참조라 순환 참조 위험이 있었습니다. 프로토콜을 `AnyObject`로 제한하고 `weak`으로 바꿨습니다.
- 지역 선택 화면은 열기만 해도 `sendRegionData(city: "서울시", gu: "강남구")`를 무조건 호출하고 있었습니다. 아무것도 고르지 않고 뒤로 나가도 홈 라벨이 "서울시 강남구"로 바뀌던 원인이라 제거했습니다.

### 남겨둔 것

상세 화면의 "좋아요", "리뷰", "나의 라멘 가게"는 `UIButton`이 아니라 `UIImageView`에 탭 제스처를 붙여 만든 것입니다. 그래서 눌렀을 때 눌린 느낌이 없고, VoiceOver가 버튼으로 읽지 않으며, 터치 영역도 아이콘 크기 그대로라 작습니다.

`UIButton`으로 교체하면 이 셋이 한 번에 해결되지만, 스토리보드 아웃렛 타입이 `UIImageView`로 잡혀 있어 코드만으로는 바꿀 수 없었습니다. 우선 접근성 정보를 붙여 VoiceOver가 버튼으로 읽도록 하고 탭 피드백을 추가해두었습니다. 실제 교체는 Xcode에서 스토리보드를 여는 시점에 하려고 합니다.

### 검증 상태

이번 작업도 Xcode가 없는 환경에서 진행했습니다. 브레이스 균형, import 누락, 삭제한 심볼의 잔존 참조는 확인했지만 컴파일은 돌려보지 못했습니다. 타입 오류나 스토리보드 아웃렛 불일치는 실제 빌드에서만 드러나므로, Codemagic 빌드로 한 번 더 확인이 필요합니다.

특히 홈 화면 사진 뒤바뀜은 응답 순서에 따라 증상이 나타났다 안 나타났다 하는 종류입니다. 한 번 정상으로 보였다고 해서 고쳐진 것은 아니므로, 여러 번 실행해서 확인하는 편이 안전합니다.
